# Trust scores and clean series for transaction data

{firm}

You have a daily panel of card transactions: several independent data sources (sensors) each report every company's
daily transaction count and dollar total. Sources sometimes misreport. Build code that says, for every row, whether
it can be trusted, and that produces a cleaned version of every series.

The point is a usable, like-for-like series for every source with as much of its history as possible. Some segments
of the data carry too little signal to be worth keeping, and those may be discarded; everything else should be kept,
repaired where it needs repair.

## What to deliver

1. **`/app/solution/score.py`**, runnable as

```
python /app/solution/score.py --input IN.csv --output OUT.csv
```

`IN.csv` has the same columns as the data above. `OUT.csv` has one row per input row, with columns
`date, ticker, source_id, confidence, clean_ct, clean_amt`:

* `confidence`, in [0, 1]: the probability that this row carries usable signal about what the company actually did
  that day, as reported or after your adjustment, worked out from the evidence in the data (how far the row sits from
  what the source would normally report, given its own noise). High means trust it; below 0.5 means do not. A change
  in a source's series can be a temporary blip or a permanent shift: once a shifted source has settled on its new
  level and you have adjusted for it, its rows carry signal again.
* `clean_ct`, `clean_amt`: a cleaned series for the row's ticker and source that is comparable like for like with
  that source's own history: what the source would have reported had it kept working the way it normally does.
  Where a row is fine, it equals the raw value. Where a row cannot be trusted, impute it. Leave a row blank only when
  it belongs to a segment you discard for low signal (and give it low confidence).

## Requirements

* **Code, point in time.** Every output for a row dated *t* may use only rows dated on or before *t*. This is
  checked for all three columns by running your script on the hidden panel truncated at hidden dates and comparing
  with a run on the whole panel.
* **No AI at run time.** You may use any tools to develop the code, but `score.py` must not call a model or any
  network service. It runs with the network off.
* **Built to scale.** Imagine running this on hundreds more sources and companies: the bar is to catch the
  obviously wrong datapoints automatically. Encode every judgment in the code, not in a list of dates or tickers.
  The code must treat every company and every source alike: no rule, setting or exception for a particular ticker,
  source id or date (source ids are shuffled on the panels your code is graded on).
* **Simple is fine.** Use complexity only where it clearly helps. Python 3.12 with pandas, numpy, scipy, statsmodels,
  scikit-learn, matplotlib, ruptures, Rbeast, prophet and statsforecast is available (fixed versions, no network);
  use any of them, or none.
* **Low-signal data.** Segments that carry no usable signal (for instance a stretch where a source has too few
  transactions for its daily numbers to mean much) may be discarded, as long as the rule is in the code so it would
  scale. Discard as little as you can: history is valuable.
* **New data.** Your script is graded on three different panels of the same kind: other companies, with their own
  tickers, dates and problems, each drawn afresh; your score is the mean over the three. Each run must finish within
  20 minutes on 2 CPUs.
* **Your own output as input.** The script must also run on a file of its own cleaned series in the input format.

## How you are scored

The grader knows which rows of the hidden panel misreport and what each source would have reported had it been
working normally.

Your score is a weighted average of three parts: 40% confidence, 40% cleaned series, 20% stability.

* **Confidence.** Scored row by row, as a probability. On the rows a problem made untrustworthy, the lower your
  confidence the better; on rows that are fine, the higher the better; both by the squared error of your confidence
  against what the row is (0 untrustworthy, 1 fine), with the untrustworthy rows and the fine rows weighing half each
  (and each kind of problem weighing the same). A constant 0.5 scores nothing. False alarms also cost: that
  score is multiplied by one half plus half the share of your alerts that touch a real problem (an alert is a run of
  rows on one source scored below 0.5, gaps of up to two days joined, a run longer than two weeks counting once per
  two weeks). A problem counts from the day it first
  shows in the data; after a lasting change, its first two weeks are untrustworthy, the weeks while it settles are
  not scored, and from then on the new level counts as fine, so confidence should rise again. A problem that builds
  up too slowly for its start to be dated counts only in the cleaned series.
* **Cleaned series.** On rows a problem affected, how much of the gap between the raw value and what the source
  should have reported your cleaned value closes (in log terms, count and dollars, each kind of problem weighing the
  same; differences within the source's own day-to-day noise are not counted), multiplied by the share of rows that
  were fine and that your cleaned series leaves within the source's own noise, and by the share of rows that should be
  kept and that you did not leave blank. A blank cleaned value on a row with a problem counts as the raw value, so a
  row left blank where it should have been imputed earns nothing.
* **Stability.** Your script is run again on its own cleaned series (same columns; counts may not be whole numbers)
  and on clean data, and the cleaned series should not be distrusted more often than clean data (extra alarms count
  against you in proportion to the size of the real problems in the panel).

The total is set to zero if the outputs are malformed, if the point-in-time check fails, if the code imports or shells
out to a model or network client, if the report is missing, if the confidence score is under 0.25 (repairing the
series without detecting its problems does not count), or if low-signal data is not dropped: a source that reports
fewer than about twenty transactions a day before it has built up steady coverage (its early history, or all of it)
must be distrusted and left blank there (at least 90% of those rows). A source that dips that low after it was
established is kept: those rows count in the cleaned-series score, so blanking them costs history.

Not scored: the panel's first year (history for your code to learn from), rows near the twenty-a-day line, the two
weeks either side of a low-signal stretch's edges, problems too small to stand out from a source's own noise, and
other debatable rows.

**The report.** That total is then multiplied by 0.5 + 0.5 x the report's score, so a weak report can halve it but a
good report cannot earn anything on its own. The report is checked against what is asked for above, on this panel
and your code's output on it: each section there, in order, with its content; every number set in the code explained;
what the output leaves unrepaired listed; claims about the output that match it; nothing from outside this page and
the panel. A report that misstates what its own output does scores zero.
